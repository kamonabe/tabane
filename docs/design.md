# tabane（束ね） ゲーム設計書（下書き v0.3）

最終更新: 2026-10-27

## 1. 概要

開発プロジェクトの「1チームのチームリーダー」として、構想検討からリリースまでを進めるシミュレーションゲーム。ブラウザ（Chrome）で遊べる。

### 目的

- **表の目的**: ちゃんと遊べる、何度も遊びたくなるゲームであること。
- **裏の目的**: 新しく配属された人や開発に興味がある人が、「組織の開発」を知り、理解するきっかけになること。説明を読ませるのではなく、遊ぶうちに「あるある」と体感できる作りにする。

### 雰囲気と言葉づかい

- 1プレイは **30分くらい**。
- 雰囲気は **ポップで柔らかく**。失敗しても責められている感じにせず、笑えるくらいの軽さにする。
- **専門用語はできるだけ避ける**。どうしても使う場合は、その場で（解説）を添える。
  - 例: 「ステコミ（えらい人たちが集まって、プロジェクトの進め方を決める会議）」
  - 例: 「技術的負債（急いで作ったせいで、あとから直すのが大変になった部分）」

## 2. プレイヤーの立ち位置（固定）

- 開発プロジェクトの中の **1チームのチームリーダー**。
- 裁量はあるが、**最終決定者でもプロジェクトの全責任者でもない**。良くも悪くも中途半端な立場。
  - 上: PM、組織長（部長以上）
  - 横: 他チーム、運用担当組織、外部ベンダ
  - 下: チームメンバ（社員・外注要員）
- この立場をメカニクスで表現する:
  - チーム内のこと（タスク割当、進め方、育成）は自分で決められる。
  - 人員追加、予算、スコープ変更、スケジュール変更は **上申** が必要。承認されるかどうかは、上位者からの信頼度と、説明の内容で決まる。却下や条件付き承認もある。
  - 上からの決定（方針転換、予算削減など）は、納得できなくても受け止めて、チームに伝えなければならない。

## 3. 1プレイの流れ

### 3.1 開始時（ランダム生成）

構想検討フェーズから始まる。毎回、次の条件がある程度ランダムに決まる。

| 項目 | 内容の例 |
|---|---|
| 開発対象 | 具体名は出さず抽象化する。規模（小・中・大）、不確実性（要件の固まり具合）、運用への影響度（止まると困る度合い）、技術的な新しさ |
| スケジュール | 全体期間（例: 3〜12か月）、マイルストーンの位置、締切の固さ |
| 初期メンバ | 人数（例: 3〜6人）、各自のスキル（設計・実装・テスト・業務知識・調整力）、経験、モチベーション、性格の傾向 |
| 予算 | 外注要員やベンダに使える枠 |

条件の組み合わせで「余裕のある案件」「最初から無理筋な案件」などが生まれ、毎回違う判断が求められる。

### 3.2 フェーズ

1. **構想検討**: 開発対象の把握、体制案（自チームでやるか、外注・ベンダを使うか）、概算の見積もり、組織長への初回説明
2. **要件定義**: 運用担当組織や関係者との要件のすり合わせ
3. **設計**
4. **開発**
5. **テスト**
6. **リリース**

ゲームを短くまとめるために、フェーズ数は後で調整してもよい。

### 3.3 ターン

- 1ターン = 1週間（仮）。
- 1プレイ30分に収めるため、全体は **24ターン前後**、1ターンあたり1分強で判断できる量にする。開始時に決まるスケジュールの長さは、ターン数ではなく「1ターンが何週分か」や締切の厳しさで表現する。
- 毎ターン、リーダー自身の時間（行動ポイント）を配分する。
  - メンバへのタスク割当、レビュー、自分で手を動かす、育成・1on1
  - 関係者との調整、会議、報告資料の準備
- リーダーが調整に時間を取られるほど、チームを見る時間が減る。この板挟みを体感させる。

## 4. 指標（パラメータ）

| 指標 | 意味 |
|---|---|
| 品質・コスト・納期（QCD） | プロジェクトの成果そのもの |
| 残作業量・進捗 | 見積もりとのずれが見える |
| 技術的負債 | 急ぐほど溜まり、後のフェーズで効いてくる |
| メンバの士気・疲労・スキル | 無理をさせると離脱や品質低下につながる |
| ステークホルダごとの信頼度 | 上申の通りやすさや、交渉の結果に効く |

数値はすべて正確に見えるわけではない。進捗は「メンバの自己申告」として見え、実態とずれることがある。

## 5. ステークホルダ

| 相手 | 主な関わり方 |
|---|---|
| PM（直属の上位） | 日々の報告・相談、上申の窓口 |
| 組織長（部長以上） | 定期報告、ステコミ。進捗や予算の説明、判断を仰ぐ場 |
| 運用担当組織 | 要望・改善依頼が途中で上がってくる。リリース後の運用を担う |
| 外部ベンダ | 打ち合わせで仕様や納期をすり合わせる。遅延や品質問題が起きることもある |
| 外注要員の会社（派遣・業務委託） | 人数、単価、期間、スキルの交渉。要員の入れ替えもある |
| 他チーム | 依存関係（相手の遅れが自チームに響く）、人の貸し借り |

会議や交渉は、選択肢を選ぶ簡単な会話形式にする（例: 「正直に遅延を報告する」「リカバリ案を添えて報告する」「様子を見る」）。

## 6. イベント（例）

- 運用担当組織から要件の追加・変更依頼
- 組織長からの方針転換、予算削減、前倒しの要求
- メンバの体調不良、異動、退職
- 外注要員の契約更新・単価交渉、要員の入れ替え
- ベンダの納品遅延、品質問題
- 他チームの遅延による待ち
- テストでの重大バグ、本番障害
- 良いイベントもある（メンバの成長、ベテランの助っ人、要件の取り下げなど）

## 7. 終了と評価

- リリースを迎えるとゲーム終了。途中でプロジェクト中止になる結末もある。
- 評価は1つの点数ではなく、複数の観点で見せる: QCD、ステークホルダの満足度、チームの状態（燃え尽きていないか、成長したか）。
- 「納期は守ったがチームが疲弊した」「遅れたが運用からは感謝された」など、複数のエンディングを用意する。

## 8. 振り返り（裏目的のための仕組み）

- プレイ後、起きた出来事を時系列で振り返る画面を出す。
- 主な出来事に「現実ではこういうこと」という短い解説を添える（例: ステコミとは何か、なぜ途中で要望が変わるのか、外注の単価交渉で何が話し合われるか）。
- ゲーム中に出てきた（解説）付きの言葉は、振り返り画面でまとめて見返せるようにする。

## 9. 画面構成（案）

- **ダッシュボード**: 週、フェーズ、QCD、残作業、主要な指標
- **チーム画面**: メンバ一覧、スキル、状態、タスク割当
- **予定・イベント**: 会議、締切、届いた依頼の一覧
- **会議・交渉画面**: 会話形式の選択
- **報告画面**: ステコミや定期報告で何をどう伝えるかを選ぶ
- **振り返り画面**: プレイ後の解説

### 見た目

- **ドット絵**を基本にする（イラストも候補）。ポップで柔らかい雰囲気に合わせ、色数を絞ったやさしい配色にする。
- メンバ、ステークホルダ（組織長、運用担当、ベンダ、外注会社の担当者など）には顔や立ち絵のドット絵を用意し、会議や交渉の画面で表情が変わるようにする。
- 絵は差し替えられる作りにする。最小の遊べる版では簡易なドット絵（仮素材）で進め、ステップ4で本番の絵に仕上げる。

## 10. 最小の遊べる版（ステップ3）の範囲（案）

- フェーズ: 構想検討〜リリースを短縮版で（全体12ターン程度、15分で遊べる量）
- ステークホルダ: 組織長（ステコミ）、運用担当組織、外注要員の会社の3つから始める
- イベント: 10種類程度
- 振り返り画面は簡易版
- セーブは無し（ステップ4で追加）
